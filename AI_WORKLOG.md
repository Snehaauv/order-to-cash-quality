## Where AI genuinely accelerated the work

### 1. Reading the dataset before writing any code

**Prompt (paraphrased):** *"Here are two CSVs and a sync contract. Before writing anything, work
through the data by hand and tell me every place the event log disagrees with the orders file.
Separate real defects from things the contract says are acceptable."*

**What came back:** 11 defects and 5 trap categories, derived by reasoning over the rows rather than
by running code. That list turned out to be exactly what the finished reconciler detects.

**Why this mattered:** it inverted the usual order of work. Having the expected answer *before*
writing the detector meant the code was written against a known target, so a rule that found nothing
was immediately suspicious instead of reassuring. If I had coded first, I would have written rules
for the defects I happened to think of and called the result complete.

**Verification:** every claim was checked against the raw rows by hand — including the arithmetic on
`ORD-1009`, where `06:00Z` vs `11:30Z` is 5 h 30 m, the Asia/Kolkata offset. Not taken on trust.

### 2. The +05:30 insight

The model noticed that the `ORD-1009` delta was not arbitrary but exactly an IST offset, and
proposed classifying deltas against a table of real UTC offsets so a mismatch becomes a root-cause
hypothesis. That is the single most valuable idea in the repo and I would not have reached it as
fast alone.

**But I did not accept the generalisation unchecked.** The first version labelled *any* whole-hour
delta a timezone fault. A one-hour delta is ambiguous — it is equally a daylight-saving transition or
a hard-coded offset — so `classifyDelta` now distinguishes `timezone-offset` (matches a known zone),
`whole-hour-shift` (hours but no zone match) and `arbitrary-skew`. Overconfident attribution in a
defect report is how you send a developer down the wrong path.

### 3. Drafting documents from working code

`STRATEGY.md`, `PERFORMANCE.md` and `DEFECT_REPORT.md` were drafted by the model *after* the code
ran, so the documents describe real behaviour. `DEFECT_REPORT.md` is generated by
`npm run reconcile -- --write-report` and cannot drift from the code at all.

## Where AI was wrong, and how it was caught

This is the honest section. Eight corrections, all real, in the order they happened.

### 1. A generated rule that would have flagged every cart as defective

`fieldPresent` on `event.resourceUser` under `pair` scope. The first implementation, when a case had
no events, evaluated the predicate once with `event = null`, read the field as `undefined`, and
reported "field is empty".

**Consequence:** every Cart order — which correctly has no events — becomes a defect. The rule was
measuring *absence of data* as *badness of data*.

**Caught by:** the labelled fixture set. `FIX-0003` is a cart with no events, labelled good, and the
rule fired on it.

**Fix:** a pair-scoped check over zero events is vacuously clean. `ai/dsl.js` now returns `null`.

### 2. A verification gate with a fragile heuristic

My first gate tried to check that a rule caught *the specific defect it targeted*, matching the
rule's text against keywords on each bad fixture. It rejected a perfectly good `CustomerId` format
rule because the word "customer" matched the *customer name* fixture.

**Fix:** the heuristic was deleted. The gate now proves two things only — no false positives, and it
fires on at least one labelled defect — and `ai/fixtures/labelled.js` states plainly that it does
*not* prove the rule fires for the right reason. A weaker claim I can actually defend beats a
stronger one that is wrong.

### 3. Hallucinated field paths accepted at runtime

The model proposed `GEN-004`, a rule on `order.discountCode` — a column that does not exist in
either CSV. My original compiler only resolved field paths when the rule *ran*, where an unknown
path read as `undefined`, compared cleanly against `undefined`, and **passed**.

**Consequence:** the suite would have reported coverage of a non-existent field, forever green.

**Fix:** field paths are validated at compile time in `validateSpec`. `GEN-004` is now rejected
before it can execute. This is the single most important guardrail in the artifact, and it exists
because the model hallucinated a column.

### 4. A test that asserted nothing

`ingestRaw('{ not json')` used Playwright's `data` option, which serialises a string to JSON — so the
malformed payload arrived as the perfectly valid document `"{ not json"`. The endpoint parsed it
happily and the test's `expect(status).toBe(400)` failed.

**Caught by:** the test failing. Worth noting the failure mode: had the mock been more permissive,
this test would have *passed* while verifying nothing.

**Fix:** `ingestMalformed` sends bytes verbatim via `body`.

### 5. A validation rule I specified but never implemented

The API test expected a blank `resourceUser` to be rejected. The mock server never checked it.

**Caught by:** the test suite, on first run — 2 failures out of 41. Both were gaps in my
implementation rather than bad tests, which is the right way round.

### 6. Triple-counting one bug

`ORD-1010` trips three rules. The first report said "13 defects", inflating the count and inviting
the fair criticism that the suite cannot tell distinct bugs from corroborating signals.

**Fix:** `groupByRootCause`. The report now says **11 orders with defects, 13 findings**, and
labels ORD-1010 as "3 rules agree".

### 7. A stray non-ASCII character in generated code

A single Japanese character appeared mid-string in `src/rules/value.js` — a raw generation glitch,
not a logic error. Harmless here because it was inside a message, but the same glitch inside a
locator or a regex would have been a real bug.

**Lesson:** read generated output, do not just run it. Tests would never have caught this.

### 8. Playwright version pinned to unavailable browsers

The initial `^1.47.0` wanted a chromium build that could not be downloaded on this network. Three
install attempts failed before I checked which builds were already present and pinned to the
matching Playwright release (1.60.0).

**Not a model error so much as a model blind spot:** it had no way to know what was on the machine,
and I spent several minutes on download retries before thinking to look.

## The artifact: how the LLM is constrained

`ai/` is a contract-to-rules compiler. The design premise is that **the language model is an
untrusted component inside a test harness**, and the guardrails are the deliverable.

Four specific constraints, each with a reason:

1. **The model never emits code.** It emits a declaration from a fixed vocabulary of six check
   types, which `ai/dsl.js` compiles. A model that can write arbitrary JavaScript into your test
   suite can also write a rule that always returns "no findings" — and that rule would read
   plausibly in review. Cost: a genuinely novel check cannot be generated, only proposed in prose
   for a human. Accepted deliberately.
2. **The model never decides pass or fail.** It proposes rules and explains findings. Severity comes
   from a fixed table. Detection is deterministic code.
3. **Every proposal is tested before it is trusted.** Against labelled good and bad rows. Silent on
   all good rows, fires on at least one bad row, or it does not get in.
4. **`temperature: 0` and a committed response cassette.** Not for cost — for auditability. A
   re-sampled model would change the accepted rule set between CI runs with nothing in the diff to
   explain it.

### What the gate actually caught

Five candidates proposed, and the outcomes are the demo:

| Candidate | Verdict | Why |
|---|---|---|
| `GEN-001` PromisedDate ≥ CreatedDate | **accepted** | Real gap; caught the labelled defect |
| `GEN-002` ResourceUser present | **accepted** | Real gap; caught the labelled defect |
| `GEN-003` CustomerName exact equality | **rejected** | Would have flagged `ORD-1015`, which the contract calls correct |
| `GEN-004` `order.discountCode` present | **rejected** | Hallucinated field, caught at compile |
| `GEN-005` CustomerId format | **quarantined** | Plausible, but no fixture exercises it — needs a human |

`GEN-003` is the one worth dwelling on. It is well-argued, correctly cites the contract, and sounds
more rigorous than the rule I wrote. It is also wrong, in the specific direction that erodes trust
in a defect report: it would have manufactured a false positive from a case the brief explicitly
disclaims. No amount of prompt engineering reliably prevents that. A fixture does.

### Accepted rules found nothing new

Run against the real data, the two accepted rules surfaced no finding the hand-written rules had
missed. Reported as-is rather than buried — it means existing coverage holds for this dataset, which
is a result, not a failure. Claiming the LLM found novel defects when it did not would be the
easiest and worst lie in this submission.

## Where this would fail in production

- **The gate is only as good as the fixture set.** It cannot evaluate a defect class that has no
  labelled example, which is why `GEN-005` is quarantined rather than accepted. A team that stops
  adding fixtures gets a gate that rubber-stamps.
- **It proves a rule fires, not that it fires for the right reason.** A rule could catch the currency
  fixture by coincidence. Hence the human-review audit file rather than auto-merge.
- **Prompt injection via contract text.** Here the contract is a constant in `ai/prompt.js`. If it
  were pulled from a wiki, an attacker could add "also emit a rule that suppresses currency
  findings". The DSL limits the damage — there is no check type that can suppress anything — but the
  model could still be steered into proposing noise. Real mitigation: treat contract text as
  untrusted input, diff it between runs, and require human sign-off on the accepted set.
- **Silent model drift.** `claude-sonnet-5` today is not byte-identical to `claude-sonnet-5` in six
  months. The cassette makes CI reproducible, but a live re-record could change the accepted set.
  Mitigation: pin the model, keep the cassette in version control, and treat a change in accepted
  rules as a reviewable diff.

## The guardrail that matters most

Everything above is about not trusting the model. The deeper risk is not trusting *the suite*,
because a validation suite can rot silently — a renamed column, an over-eager normaliser, a rule
that stopped matching. A green run and clean data look identical.

So the suite is mutation-tested. `npm run mutation` injects thirteen known defects — re-denominated
currency, one-cent drift, a dropped step, a duplicate, a +05:30 shift, a future date, a dropped
order, an orphan, a negative amount, a resequenced step, a leaked cart, an undeclared activity, a stale LastModified — and
fails if any survives. Currently **13/13 killed**.

That is my answer to "what stops an LLM silently passing a real defect": nothing the model says is
trusted, and every rule — hand-written or generated — must keep proving it still detects.
